# Discord PM 질문과 계획서

2026-10-22 변경.

`/지시`로 직접 등록하거나 백서진과의 대화에서 등록에 동의한 뒤 PM이 먼저 요구사항을 확인한다. 백서진의 `create_order`는 등록 제안만 준비하며, 다음 사용자 답변이 명확한 동의일 때 `respond_order_proposal`로 등록한다. 자세한 대화 규칙은 [HERMES-SOUL.md](HERMES-SOUL.md)를 따른다. 목적·대상·범위·핵심 동작·성공 기준에 불명확한 점이 있으면 계획서나 견적을 만들지 않고 질문만 보낸다.

프로젝트에는 작업·기획·할일·결재함·완료·막힘·사무실-대화 채널을 함께 만든다. 기존 프로젝트는 시작할 때 빠진 채널을 보충하고, 등록된 프로젝트 카테고리를 다시 만들 때도 같은 구성을 채운다. 이미 있는 채널은 재사용한다. 어느 하위 채널에서 `/지시`를 써도 해당 프로젝트로 고정한다.

채널 생성·보충의 Discord 관리 주체는 백서진(비서실장)이다. LINDA에는 채널 관리 권한을 요구하지 않는다. 인증과 서버 역할 순서는 [DISCORD-AUTHORITY.md](DISCORD-AUTHORITY.md)를 따른다.

질문은 PM 봇이 프로젝트의 기획 채널에 올린다. 프로젝트별 채널을 알 수 없으면 지시가 들어온 채널이나 비서실을 사용한다. 질문 메시지에 **답장**으로 번호별 답변을 보내거나 **답변하기** 버튼을 쓴다. 답장에 PM 멘션을 유지하면 Discord가 메시지 내용을 제공한다. 관련 없는 일반 채팅은 답변으로 쓰지 않는다. 이전 질문과 중복 답변은 거부한다. 요구사항이 처음부터 충분히 명확하면 질문 없이 계획서를 작성할 수 있다.

PM은 원문과 모든 질문·답변을 다시 읽는다. 부족한 답변에는 후속 질문을 보내고, 충분히 이해했을 때 계획서를 쓴다. 계획 작성 중 새 질문이 생겨도 질문 단계로 돌아간다. 미해결 질문이 있는 계획서는 관문이나 CEO 승인으로 넘어갈 수 없다. 업데이트 전 결재 대기 중이던 질문 포함 계획서는 엔진이 결재를 회수하고 별도 질문으로 옮긴다.

질문과 답변은 `system_state`의 `clarification:<orderId>`에 저장하므로 프로세스 재시작 후에도 이어진다. 이전 질문이나 중복 답변은 거부한다. 답변과 결재는 기존처럼 CEO 계정만 할 수 있다.

Discord 전송 시 내부 JSON 기록은 직원 본인이 설명하는 한국어 문장과 문단, 필요한 목록으로 바꾼다. 거울 통역도 보낸 직원의 말투로 1인칭으로 설명한다. 통역 모델이 없거나 실패하면 완료·검토·교정·회의·문서 기록의 뜻을 보존하는 로컬 변환기를 사용한다. 자체 확인을 최종 검토로 부풀리거나 미확인 근거를 감추지 않는다. 긴 전송 메시지는 Discord 제한 안에서 나누고, 계획서의 결재 버튼은 마지막 조각에 붙인다. 메시지를 수정할 때 앞 조각들도 함께 갱신한다. 거울의 기존 요약 길이와 사무실 화면 링크 정책은 유지한다.

PM의 계획서는 해당 프로젝트 결재함에, 담당 AI의 착수·재작업과 검토자의 검토 소식은 할일에, 담당 AI의 완료 보고와 Git 고양이의 푸시 결과는 완료에 올라간다. 작업 대화도 프로젝트의 사무실-대화에서 해당 역할의 봇으로 보낸다. 직원에게 일을 맡기는 제안도 그 직원의 봇으로 보낸다.

발신 봇과 실제 채널은 메시지 ID와 함께 저장한다. 결재·답변 버튼은 직원 봇에서도 공통 CEO 권한 검사를 거치고, 결정 뒤에는 원래 보낸 봇이 원래 메시지를 수정한다. 담당 직원 봇이 끊기면 해당 메시지는 재시도를 기다리며 LINDA로 대체하지 않는다. LINDA는 명령 접수와 전체 시스템 상태 안내를 맡는다. 프로젝트에 속하지 않는 공용 거울의 웹훅 장애 복구는 기존대로 유지한다.

검증: `npm run typecheck`, `npm test -- --reporter=dot --testTimeout=15000 --maxWorkers=2`. 질문/답변/후속 질문/기존 결재 회수/JSON 통역 실패/긴 메시지에 대한 회귀 테스트를 포함한다.

## 직원에게 대화로 일을 맡기기

직원을 멘션해 대화를 시작하고, 이후에는 해당 직원의 답장에 답하거나 다시 멘션한다. 각 직원은 자기 성격과 말투로 대화하며 인사·감정·아이디어 탐색을 바로 업무로 바꾸지 않는다. 목적·범위·핵심 동작이 모호하면 먼저 묻는다. 대화에는 업무 실행 카드 대신 별도의 대화 지침을 사용하고, 이전 사용자 발언과 직원 답변을 실제 차례대로 전달한다. 연달아 보낸 말은 직원별로 순서대로 처리한다.

최근 대화는 직원·채널별로 최대 20회·6시간·16000자 안에서 DB에 보관해 재시작 뒤에도 이어진다. 1분마다 만료 기록을 정리하며 다른 직원·채널과 섞지 않는다. 해당 직원을 불러 “대화 초기화”, “최근 대화 잊어줘”, “대화 기억 지워줘”라고 말하면 이 채널의 기억과 대기 중인 직접 작업 제안을 지운다. 실제 티켓·결재 기록은 바꾸지 않는다. 기억은 화면·대화 로그·보고용 이벤트에 추가하지 않는다.

사장님과의 대화는 GPU 대기열에서 일반 작업·거울 통역보다 먼저 처리한다. 이미 실행 중인 호출은 중단하지 않으며 오래 기다린 작업의 우선 처리 규칙은 유지한다. 같은 직원에게 동시에 보낸 메시지는 최대 4개까지 순서대로 처리한다. 작업의 자연어 동의는 실제 확인 질문이 Discord에 전송된 뒤에 보낸 메시지만 인정한다.

충분히 이해하면 전체 요청과 마무리 조건을 한 답장에 정리하고 “이 내용으로 제가 맡아서 진행할까요?”라고 묻는다. 다음 메시지에서 “응”, “응, 진행해”, “그 내용으로 시작해 주세요”처럼 분명히 동의하면 그 직원에게 직접 맡긴 작업을 시작한다. 수정 제안은 “응, 반영해”로 확정한다. 버튼도 계속 사용할 수 있다. 이것은 직원에게 직접 맡기는 기존 작업 경로의 확인이며, 결재함에 올라온 계획서·푸시·배포 결재는 기존 버튼 절차를 따른다.

추가 질문·수정·거절을 하면 이전 제안은 닫고 대화를 이어간다. 새 범위에는 다시 확인이 필요하다. 같은 메시지의 재전송, 다른 직원·채널·사용자의 동의, 30분이 지난 제안, 이전 확인 질문에 대한 답장으로 새 작업을 시작할 수 없다. 제안과 확인 질문은 LINDA 대신 해당 직원이 자기 답장으로 보낸다.

실제 로컬 모델 대화 확인: `node packages/orchestrator/src/sim/staff-conversation-check.ts` (메모리 DB만 사용, Discord 전송·업무 실행 없음).

여러 차례 대화 확인: `node packages/orchestrator/src/sim/local-dialogue-check.ts`. 짧게/질문 없이 말해 달라는 요청 유지, 정정한 이름·색 회상, 일상으로 화제 전환을 실제 로컬 모델로 검증한다.
